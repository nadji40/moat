Thirduni, autumn 2026

Agents are about to spend real money. We watch the decision.

Moat is the risk layer for AI agent payments. It sits in front of the mandate and asks the question the rails don't: was this decision the user's, or the attacker's?

See the product See the open roles

Everyone is building the rails.

The rail owners are building the controls.

The fraud layer has no owner.

That is the gap Moat fills.

What Moat actually checks.

Three questions the payment rails never ask.

Provenance

Moat matches payment fields against registered user intent, allowlists and observed tool results. Policy decides which sources a field may use: a price can come from a page while a new recipient still needs approval. A match records an observed source; it does not prove intent.

Behaviour

The prototype applies payment-call limits per session and per minute. Next we will test replay, cumulative spending and repeated-payment patterns. Learned behavioural profiles are later work, after we have representative traces.

Evidence

Each verdict records the payment fields, matched sources and policy decisions in a signed, hash-chained log that can be verified offline. It supports investigation by showing what Moat recorded; it does not establish that a payment was correctly authorised.

Moat is the authorization layer agents call before they spend.

Not a payment gateway. A decision gateway: the agent hands over the action and the context that produced it, and Moat answers before the money moves.

          allow
          
The payment satisfies the configured policy, including its source requirements, spending cap and call limits. The call proceeds with a signed decision record.

        

        

          step-up
          
The common case. A field came from somewhere untrusted, so the agent pauses and asks you. A product that only blocks gets ripped out in a week. One that escalates gets kept.

        

        

          deny
          
Policy says no and there is no one to ask. The payment never leaves the runtime, and the evidence bundle says exactly which field, from which source, tripped it.

As an MCP proxy · built

          
The prototype observes tool results and intercepts configured payment calls over MCP, with stdio and Streamable HTTP support. The host registers user intent separately and must preserve approval details to complete a step-up.

What is built. What we deliver next.

      
Phase one is implemented. The next phase targets four weeks of evaluation and hardening, ending in a reproducible research release. These are delivery targets, with completion judged by the checks below.


      

        

          
Built · working prototype

          
MCP forwarding, source matching, policy evaluation, payment interception, intent registration, approval and resume, and signed evidence with offline verification. Integration tests cover the payment flow and Streamable HTTP.

        

        

          
Built · first evaluation

          
A mock marketplace and payment server, ten attack cases, a scripted-agent runner and initial model runs. Payments are simulated. These exploratory runs do not yet establish reliability, false-positive rates or production readiness.

        

      

      
Known gaps guide the next phase: replay and under-cap inflation can pass the current policy, some agent hosts discard the details needed for approval, and the intent API needs authentication before use beyond a trusted local environment.

Week 1 · establish the baseline

          
Add legitimate purchases alongside the attack cases. Verify the complete approval flow and evidence logs. Define scoring and compare no protection, a spending cap, an allowlist and Moat under the same tasks.

        

        

          
Week 2 · close gaps, freeze the evaluation

          
Address replay, amount binding and host approval handling. Separate development attacks from held-out cases, then freeze the policy, implementation and evaluation set before final measurement.

        

        

          
Week 3 · measure security and usefulness

          
Repeat runs across the selected models and report attack success, legitimate task completion, unnecessary blocks, approval burden and added latency. Publish run counts and uncertainty, including failures.

        

        

          
Week 4 · publish a reproducible release

          
Package the arena, corpus, configurations, sanitised run records, demo and technical report with reproduction instructions. A broader paper, SDKs and payment-provider pilots follow the evidence from this release.
